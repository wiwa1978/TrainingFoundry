# Microsoft Foundry Workshop Series — Proposed Agenda

## Section 1 — Foundry Fundamentals (80 minutes)

| Time | Topic | Content | Examples | Use cases |
| --- | --- | --- | --- | --- |
| 5 minutes | **Foundry Fundamentals** | Models, projects, agents, tools, knowledge, evaluations and monitoring. Show where Build and Operate fit in the portal. Introduce the Contoso Field Services scenario. | • Portal Foundry overview: resource → project hierarchy.<br>• Portal left navigation: Build versus Operate.<br>• App use cases gallery: Media / Agents toggle and modality filters.<br>• App Text Chat (GPT-5.5): ask one Contoso question as the destination experience. | — |
| 7 minutes | **Models and deployments** | Model catalog, deployment choice, quality/latency/cost trade-offs, project endpoint and authentication. Keep the theory brief. | • Portal model catalog and model card.<br>• Portal deployments list and deployment details: version, region, TPM/quota and content-filter binding.<br>• App Text Chat: compare two deployments side by side.<br>• App Reasoning Arena: compare reasoning deployments and point to latency and token usage.<br>• Slide project endpoint and `DefaultAzureCredential` snippet. | • **Text Chat** — direct streaming to one normal model deployment.<br>• **Text to Image** — image-generation model deployment.<br>• **Image to Image** — image-edit model deployment.<br>• **Foundry GPT Audio** — audio-generation model deployment.<br>• **Realtime Speech in / Speech Out** — realtime model deployment. |
| 5 minutes | **Services** | Map the Foundry services in the UI and explain how they fit together: models, agents, tools, knowledge, memory, guardrails and data. | • Portal left navigation: models, agents, services, tools, knowledge, memory, guardrails and data.<br>• Portal Build versus Operate split.<br>• App use cases gallery as the entry point for the available experiences. | • **Content Extractor** — Content Understanding.<br>• **Azure Translator** — Azure Translator service.<br>• **Azure Language – Text Analytics for Health** — specialized Language workload.<br>• **Browser based Voice** and **STT-Chat-TTS** — application voice pipelines.<br>• **Language Learning** — Speech pronunciation assessment plus model response and synthesis.<br>• **Azure Speech Text to Speech** and **Azure Speech Text to Speech Avatar** — Speech services.<br>• **Recorded Audio Transcription** and **YouTube Video Transcription** — transcription services.<br>• **Captioning**, **Dubbing** and **Video Translation** — media-processing workflows.<br>• **Azure Speech Live Translation** — Speech translation.<br>• **Realtime Transcription WebRTC**, **Realtime Transcription WebSockets**, **GPT Realtime Translation WebRTC**, **GPT Realtime Translation WebSockets** — realtime Foundry/Speech protocols.<br>• **Voice Live travel Concierge** and **Live Chat Avatar** — Voice Live/Speech realtime services. |
| 18 minutes | **Agents** | Explain the difference between prompt agents and hosted agents, including instructions, versioning, invocation, runtime ownership, identity, scaling, endpoints, operational responsibility and cost. Use the agent playground and details view to create and refine a first prompt agent, while saving the hosted-agent deployment for Section 2. | • Portal Agents list: open the pre-created Contoso Field Services agent.<br>• Portal Instructions pane: read the system prompt as the agent program.<br>• Portal Playground: run a Contoso request.<br>• Portal Versions: switch v1 → v2 and rerun the same prompt.<br>• Slide Responses API call shape and prompt-agent versus hosted-agent decision table.<br>• Slide architecture and ownership diagrams; point to the existing hosted deployment without opening it.<br>• App rerun the same request and ask where it is executing. | • **Azure Architect Agent** — prompt-agent implementation.<br>• **Investment Planner Prompt** — prompt agent with instructions, Code Interpreter and toolbox MCP.<br>• **Hosted Agent** — application-owned hosted-agent runtime.<br>• **Retail Agent** — multi-agent/retail orchestration. |
| 12 minutes | **Tools, MCP and toolbox** | Built-in tools, file search, custom functions, remote MCP and reusable toolboxes. Emphasize that tools are capabilities selected by the model, not hard-coded branches. | • Portal Agent Tools tab: show the attached list.<br>• Portal Web Search: ask a time-sensitive question and expand the model-selected tool call.<br>• Portal File Search: ask against an uploaded Contoso file.<br>• Portal Custom Function: show the registered schema; use a slide for implementation code.<br>• Portal Microsoft Learn MCP: expand the invocation and result.<br>• Portal Toolbox: attach the same tool set to a second agent without rewiring. | • **YouTube Video Summarization** — external URL/caption retrieval followed by summarization.<br>• The agent examples use the same **toolbox/MCP** concepts, but the media workflows themselves are not Foundry agents. |
| 8 minutes | **Memory** | Explain how memory supports continuity across conversations and how it differs from tools and grounded knowledge. | • Portal Memory: start a new thread, reference an earlier turn and show recall.<br>• Cut candidate if running late: mention Toolbox on a slide only. | — The gallery workflows do not implement Foundry Memory; keep this slot portal-only. |
| 13 minutes | **Knowledge** | Explain the RAG flow and introduce Foundry IQ: source → chunks/index → knowledge source → knowledge base → MCP tool → cited answer. Explain why this is more deliberate than putting documents in a prompt. | • Slide the chain: source → chunk → index → knowledge source → knowledge base → MCP tool → cited answer.<br>• Portal Knowledge Sources: open the Contoso source.<br>• Portal Azure AI Search index: show fields and sample chunks.<br>• Portal Knowledge Base: show the MCP tool it exposes.<br>• Portal grounded agent: ask a citation-requiring question and follow the citation to the chunk.<br>• App Document Q&A: show the build-it-yourself version with Azure AI Search.<br>• Contrast with File Search from the previous slot. | • **Document Q&A** — application-managed Azure AI Search RAG with Foundry embeddings and a chat model. |
| 12 minutes | **Recap and hand-off** | The agent now has a model, tools, memory and grounded knowledge. The remaining questions are safety, quality, identity, observability, release and cost. | • Slide what we built in one diagram.<br>• Portal open the Operate section once—evaluations, tracing and guardrails—then close it as the introduction to Section 2.<br>• Q&A buffer. | — |

## Section 2 — End-to-End Enterprise AI (80 minutes)

| Time | Topic | Content | Examples | Use cases |
| --- | --- | --- | --- | --- |
| 5 minutes | **Recap: build to operate** | Revisit the Section 1 agent and frame the four operational questions for this session: can we observe it, evaluate it, protect it and release it safely? Briefly acknowledge identity, permissions and data access as cross-cutting foundations. | • Slide before/after architecture, side by side.<br>• Slide the four session themes as a checklist.<br>• Mention identity, permissions, Auth & OBO as foundations without opening a separate demo. | — |
| 20 minutes | **Observability** | Focus on Traces, Insights, Monitor and Application Insights. Follow a request across model, tool and retrieval spans to identify latency, failures and token usage, while keeping telemetry privacy-aware. | • Portal tracing — open the trace from the guardrail prompt run earlier.<br>• Portal expand the span tree: model call, tool call, retrieval.<br>• Portal latency per span and token counts per call — point at the expensive one.<br>• Azure Application Insights — show the same request as an end-to-end transaction.<br>• Portal quota/usage view on the deployment → cost conversation.<br>• Portal prompt/response capture setting — state the privacy trade-off explicitly. | — Use the already mapped workflows as trace examples; observability is cross-cutting rather than a separate use case. |
| 20 minutes | **Evaluation & Optimization** | Focus on the Foundry Evaluation and Optimize experiences. Use golden and safety datasets, evaluators and version comparisons to assess quality and safety, identify regressions and decide what should be improved before release. | • Portal evaluation datasets — golden set and safety set, show a few rows.<br>• Portal the completed baseline run — evaluators used and scores; do not start a run live.<br>• Portal the completed second run against changed instructions.<br>• Portal comparison view — show the score delta.<br>• Portal drill into 2–3 failed rows and read one out loud.<br>• Portal Optimize view — show how evaluation evidence informs improvement.<br>• Slide threshold → improve, promote or block decision. | • **Side by Side – Text Chat** — golden-set response quality comparison.<br>• **Reasoning Arena** — correctness, reasoning quality, latency and token-cost comparison.<br>• **Side by Side – Text Image** — image quality and prompt adherence comparison.<br>• **Side by Side Recorded Audio Transcription** — transcript accuracy comparison.<br>• **GPT Realtime Translation WebRTC/WebSockets** — regression checks after changing realtime deployments. |
| 20 minutes | **Guardrails** | Demonstrate how different guardrails shape agent behavior. Use application checks, Content Safety, hosted-agent RAI policy, prompt injection resistance and human review for consequential actions. Treat user input, retrieved content and tool output as data. | • Portal content filter / RAI policy on the deployment — categories and severity thresholds.<br>• Slide the guardrail layers: app check → Content Safety preflight → RAI policy → agent instructions.<br>• App guardrail test panel — paste prepared prompts, never type them: ① injection attempt → blocked/resisted, ② unsupported Sev 1 escalation → needs review, ③ invented policy → refused, no citation offered.<br>• After each example, name which guardrail caught it — that is the teaching point. | • **Text Chat — Guardrail test** — run prepared prompts against the selected chat deployment and inspect the safety result.<br>• **Text Chat — Side-by-side guardrails** — compare the behavior of two guardrail policies/configurations on the same prompt.<br>• **Azure Language – PII Redaction** — protect sensitive text before model processing.<br>• Guardrails apply to all mapped model, service, knowledge and agent workflows. |
| 15 minutes | **Operate** | Discuss how a governed agent is managed in production: immutable versions, draft testing, promotion, blue/green rollout, rollback and configuration per environment. Connect release decisions to evaluation results and operational ownership. | • Portal agent versions list — show that versions are immutable.<br>• Portal the prepared draft — smoke-test it in the playground.<br>• Portal promote green while blue remains available.<br>• Portal endpoint/traffic configuration pointing at green.<br>• Portal roll back to blue, live — then roll forward again.<br>• Slide tie back: the evaluation delta authorized the promotion.<br>• Briefly mention quotas, cost attribution, ownership and Agent 365 as the broader operate context. | — The agent modules mapped under **Agents** are the release/rollback examples; media workflows remain model/service demonstrations. |
